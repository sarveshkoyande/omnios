# Postgres migration (draft — not yet active)

Today the app persists everything as **SQLite files + a file blob store under `DATA_DIR`**
(`strategy/paths.py`). In production this is durable because `render.yaml` mounts a
**persistent disk** at `/var/data` and sets `OMNI_DATA_DIR=/var/data`. That already fixes
the "nothing is retained across deploys" problem.

This document is the path to move the **writable** stores onto a managed **Postgres** when
you want horizontal scaling or a disk-free service. The read-only knowledge base
(`omni_kb.db`) stays a committed SQLite snapshot either way — it is never written at runtime.

> **Status:** `strategy/db.py` implements the dual-dialect layer and its SQL/DDL
> translation is unit-tested (`python strategy/db.py`), **but the Postgres query path has
> not been run against a real Postgres server** (the dev machine has no Docker/psql).
> Do the "Verify" step against a real Postgres before flipping any store over.

## How the layer works

`strategy/db.py` is selected by the `DATABASE_URL` env var:

- **unset** → `db.connect("campaigns")` returns a normal `sqlite3` connection to
  `<DATA_DIR>/campaigns.db`. Identical to today; zero behaviour change.
- **set to a `postgres://…` URL** → returns a psycopg connection wrapped to mimic the small
  `sqlite3` surface the stores use, translating on the way:
  - `?` → `%s`
  - `INSERT OR IGNORE INTO t …` → `INSERT INTO t … ON CONFLICT DO NOTHING`
  - plain `INSERT` into an id-table → `… RETURNING id`, so `cursor.lastrowid` still works
  - `sqlite3.Row` → a `Row` adapter supporting positional, by-name, `dict()`, and unpacking
  - DDL: strips `PRAGMA`, `INTEGER PRIMARY KEY` → `BIGINT GENERATED BY DEFAULT AS IDENTITY`,
    `CREATE VIEW IF NOT EXISTS` → `CREATE OR REPLACE VIEW`, `BLOB` → `BYTEA`

`ON CONFLICT(col) DO UPDATE … excluded.*` (brand_memory, awards, market-intel) is already
identical in both dialects — no change needed there.

## Steps

1. **Dependency:** add `psycopg[binary]>=3.2` to `requirements.txt`.
2. **Stores:** in each store, replace the local connection with the layer. The SQL bodies
   stay exactly as they are.
   - `projects.py`, `brand_memory.py`: `sqlite3.connect(DB_PATH)` → `db.connect("projects")`
     / `db.connect("brand_memory")`; drop `row_factory`/`PRAGMA` lines (the layer sets them).
   - `campaign_store.py`, `awards_store.py`, `brand_lifecycle.py`: `_conn()` → `db.connect("campaigns")`.
     `init_db()` still calls `conn.executescript(SCHEMA_PATH.read_text())` — the layer
     translates the DDL.
3. **Blobs → `bytea`:** add a `blob_data(blob_key TEXT PRIMARY KEY, data BLOB)` table to
   `db/campaign_content_schema.sql` (already `BYTEA` after translation). Make
   `blob_store.put/get/exists` write/read that table when `db.IS_PG` (keep the file path for
   local SQLite). Set `storage_uri = f"pg://blob/{key}"` on Postgres.
4. **Seeding:** `bootstrap.seed_library()` already rebuilds everything from committed inputs;
   with `DATABASE_URL` set it will build straight into Postgres. Run it once against the new
   DB (it is idempotent). The KB copy step is unchanged.
5. **render.yaml:** add a Render Postgres instance and wire `DATABASE_URL`:
   ```yaml
   databases:
     - name: omni-pg
       plan: free            # note: Render's free Postgres expires after 90 days
   services:
     - type: web
       # …
       envVars:
         - key: DATABASE_URL
           fromDatabase: { name: omni-pg, property: connectionString }
   ```
   The persistent disk can then be removed (or kept only for the read-only KB snapshot).

## Verify (must do on a real Postgres before switching)

```
DATABASE_URL=postgres://…  python -c "import sys; sys.path.insert(0,'strategy'); \
  import campaign_store; campaign_store.init_db(); print(campaign_store.library_stats())"
DATABASE_URL=postgres://…  python strategy/bootstrap.py     # seeds the library into PG
```
Then run a full chat flow and confirm a project + campaign survive a redeploy.

## Watch-outs discovered while drafting

- **`lastrowid`** is the main risk. The layer appends `RETURNING id` only for INSERTs into
  the known `ID_TABLES`. If you add a new table with an `id` PK, add it to that set.
- **`INSERT OR IGNORE` + `lastrowid`**: on conflict, `ON CONFLICT DO NOTHING` returns no row.
  No current caller reads `lastrowid` after an `OR IGNORE` (they re-`SELECT`), so this is safe
  today — keep it that way.
- **One Postgres database holds all tables** (projects/campaigns/brand_memory). Their table
  names are globally distinct, so there is no collision; `db_name` is only used to pick the
  SQLite file locally.
