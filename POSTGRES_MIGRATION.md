# Postgres migration (wired in — activated by `DATABASE_URL`)

Today the app persists everything as **SQLite files + a file blob store under `DATA_DIR`**
(`strategy/paths.py`). In production this is durable because `render.yaml` mounts a
**persistent disk** at `/var/data` and sets `OMNI_DATA_DIR=/var/data`. That already fixes
the "nothing is retained across deploys" problem.

This document describes moving the **writable** stores onto a managed **Postgres** for
horizontal scaling or a disk-free service. The read-only knowledge base (`omni_kb.db`) stays
a committed SQLite snapshot either way — it is never written at runtime.

> **Status (now wired in):** every writable store now opens its connection through
> `strategy/db.py`'s `db.connect(...)`, so setting `DATABASE_URL=postgres://…` routes them
> all to Postgres and leaving it unset keeps the identical SQLite behaviour. `requirements.txt`
> ships `psycopg[binary]`. The Postgres itself is **Prisma Postgres** (a free-tier hosted
> Postgres from prisma.io) rather than Render's own managed database — Render only receives
> the connection string as a manually-set `DATABASE_URL` secret in `render.yaml`; Prisma's
> ORM/schema tooling is not used anywhere, only its Postgres hosting. The SQL/DDL translation
> is unit-tested (`python strategy/db.py`) and the full SQLite path is smoke-tested
> end-to-end. **The one thing still not exercised is the live psycopg query path against a
> real Postgres server** (the dev machine has no Docker/psql) — run the "Verify" step against
> the actual Prisma Postgres instance before trusting production traffic to it.

**Stores routed through the layer (all writable stores):** `projects`, `brand_memory`,
`campaign_store` (+ `awards_store`, `brand_lifecycle`, sharing `campaigns`), `hcp_360`,
`orchestration_store`, `tab_chat`, and `blob_store` (bytes → the `blob_data` BYTEA table on
Postgres). `hcp_360`/`orchestration_store`/`tab_chat` were added after this doc's first
draft and are now included.

## How the layer works

`strategy/db.py` is selected by the `DATABASE_URL` env var:

- **unset** → `db.connect("campaigns")` returns a normal `sqlite3` connection to
  `<DATA_DIR>/campaigns.db`. Identical to today; zero behaviour change.
- **set to a `postgres://…` URL** → returns a psycopg connection wrapped to mimic the small
  `sqlite3` surface the stores use, translating on the way:
  - `?` → `%s`
  - `INSERT OR IGNORE INTO t …` → `INSERT INTO t … ON CONFLICT DO NOTHING`
  - plain `INSERT` into an id-table → `… RETURNING id`, so `cursor.lastrowid` still works
  - `INSERT OR REPLACE INTO t …` → plain `INSERT INTO t …` (its only caller, hcp_360's bulk
    load, always inserts into a freshly-emptied table, so no conflict occurs at runtime)
  - `sqlite3.Row` → a `Row` adapter supporting positional, by-name, `dict()`, and unpacking
  - `executemany` and `rollback` are also exposed on the wrapper (hcp_360 bulk-loads with
    `executemany`; `rollback` lets `projects._conn` swallow a duplicate-column `ALTER` on
    Postgres without poisoning the transaction)
  - DDL: strips `PRAGMA`; **column-aware** PK translation — a column literally named `id`
    (incl. `id INTEGER PRIMARY KEY AUTOINCREMENT`) → `BIGINT GENERATED BY DEFAULT AS
    IDENTITY PRIMARY KEY`, while a *natural* integer PK (e.g. hcp_360's `npi_number__c`,
    whose value is inserted explicitly) → plain `BIGINT PRIMARY KEY` with any `REFERENCES`
    tail preserved; `CREATE VIEW IF NOT EXISTS` → `CREATE OR REPLACE VIEW`; `BLOB` → `BYTEA`

`ON CONFLICT(col) DO UPDATE … excluded.*` (brand_memory, awards, market-intel, orchestration)
is already identical in both dialects — no change needed there.

## What was done (all applied)

1. **Dependency:** `psycopg[binary]>=3.2` added to `requirements.txt` (lazy-imported, so the
   SQLite path never needs it).
2. **Stores:** every writable store's `_conn()` now returns `db.connect("<db_name>")`, with
   the redundant `row_factory`/`PRAGMA` lines dropped (the layer sets them on SQLite):
   - `projects.py` → `db.connect("projects")`; its runtime column migrations now use plain
     `ALTER TABLE ADD COLUMN` + `conn.rollback()` on the duplicate-column error, which works
     on both dialects (SQLite has no `ADD COLUMN IF NOT EXISTS`).
   - `brand_memory.py` → `db.connect("brand_memory")`.
   - `campaign_store.py`, `awards_store.py`, `brand_lifecycle.py` → `db.connect("campaigns")`;
     `init_db()` still `executescript`s the schema (the layer translates the DDL).
   - `hcp_360.py` → `db.connect("hcp_360")` (bulk load uses the wrapper's `executemany`).
   - `orchestration_store.py` → `db.connect("orchestration")`.
   - `tab_chat.py` → `db.connect("tab_chat")`.
3. **Blobs → `bytea`:** a `blob_data(blob_key TEXT PRIMARY KEY, data BLOB)` table was added to
   `db/campaign_content_schema.sql` (becomes `BYTEA`). `blob_store.put/get/get_text/exists`
   branch on `db.IS_PG`: Postgres reads/writes `blob_data` (and `storage_uri = pg://blob/<key>`),
   SQLite keeps the exact filesystem behaviour.
4. **db.py fixes required by the newer stores:** `INTEGER PRIMARY KEY AUTOINCREMENT` handled;
   PK translation made column-aware (natural PKs stay plain); `INSERT OR REPLACE` handled;
   `executemany`/`rollback` added to the wrapper; `sync_event` added to `ID_TABLES`. New
   self-tests cover all of these (`python strategy/db.py`).
5. **Seeding:** `bootstrap.seed_library()` already rebuilds everything from committed inputs;
   with `DATABASE_URL` set it builds straight into Postgres (idempotent). KB copy unchanged.
6. **render.yaml + hosting:** the Postgres database is **Prisma Postgres** (prisma.io/postgres),
   hosted outside Render — not Render's own managed Postgres, and Prisma's ORM is not used
   anywhere in the app (every store still speaks plain SQL via `strategy/db.py`'s psycopg
   wrapper; only the connection string comes from Prisma). Because it lives outside Render's
   account, Render can't auto-provision it, so `DATABASE_URL` is a manually-set secret
   (`sync: false`) rather than a `fromDatabase` reference. To activate:
   1. Create a free Prisma Postgres database at https://console.prisma.io (or via
      `npx prisma init --db` locally) and copy its connection string.
   2. In the Render dashboard for `omni-data-hub` → **Environment**, set `DATABASE_URL` to
      that connection string.
   3. Redeploy (or it picks it up on the next deploy). No other Render config is needed —
      `render.yaml` already declares the `DATABASE_URL` env var slot.
   The persistent disk is kept for the read-only KB snapshot (`omni_kb.db`) and the cognee
   memory layer; it could be removed if those move too.

## Verify (still required — the live psycopg path has not been run against a real Postgres)

```
DATABASE_URL=postgres://…  python -c "import sys; sys.path.insert(0,'strategy'); \
  import campaign_store; campaign_store.init_db(); print(campaign_store.library_stats())"
DATABASE_URL=postgres://…  python strategy/bootstrap.py     # seeds the library into PG
```
Then run a full chat flow and confirm a project + campaign survive a redeploy.

## Watch-outs

- **`lastrowid`** is the main risk. The layer appends `RETURNING id` only for INSERTs into
  the known `ID_TABLES`. If you add a new table with an autoincrement `id` PK, add it to that
  set (this is why `sync_event` had to be added).
- **`INSERT OR IGNORE` + `lastrowid`**: on conflict, `ON CONFLICT DO NOTHING` returns no row.
  No current caller reads `lastrowid` after an `OR IGNORE` (they re-`SELECT`), so this is safe
  today — keep it that way.
- **`INSERT OR REPLACE`** is translated to a plain `INSERT` — correct only because its single
  caller (hcp_360 bulk load) always writes into a freshly-emptied table. A future caller that
  needs REPLACE to overwrite an *existing* row on Postgres must add an explicit `ON CONFLICT
  … DO UPDATE` itself; the layer can't infer the conflict-target columns from the SQL text.
- **Natural integer PKs must not become IDENTITY.** DDL PK translation keys off the column
  name: only `id` becomes an `IDENTITY`; anything else (e.g. hcp_360's NPI columns) stays a
  plain `BIGINT`. If you ever add a surrogate autoincrement PK under a different name, teach
  `_translate_pk` about it.
- **One Postgres database holds all tables** (projects/campaigns/brand_memory/hcp_360/
  orchestration/tab_chat). Their table names are globally distinct, so there is no collision;
  `db_name` is only used to pick the SQLite file locally.
