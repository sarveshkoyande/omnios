Ideation

Brand, Campaign & Engagement Plan: information architecture

Date: 2026-09-24 Topic: brand-campaign-engagement-plan-ia repo-grounded

Focus: How Omni OS should model and navigate the relationship between a brand, its campaigns, and an "engagement plan" — how a new brand gets created and managed, whether campaigns are ad hoc or roll up into a formal plan, how a user actually creates an engagement plan today, and how navigation should be spaced out so brand-, campaign-, and flow-level concepts stop mixing together.

Codebase Context

Two parallel, disconnected "unit of planning work" data models exist today. project (strategy/projects.py, strategy/orchestrator.py) is a generic record that, when five agents run (planner/intel/strategy/inspiration/activation), composes a phase-gated narrative document Omni OS calls a "Brand Engagement Plan" — stored on the project row, one project per plan. brand (strategy/brand_journey.py + config/brand_kits.json, shipped 2026-09-24) is a brand entry with its own five-step agentic intake (Brief/Audience/Message/Kit/Flow) that produces a confirmed kit plus one rules-built CampaignFlow — deterministic and auditable by design (R16/R17).

There is no bridge between them. No campaign or project carries a brand_id; orchestrator.run_agents() takes brand as a bare string. A user can run a Brand Journey and a project-based Engagement Plan for the same brand with zero cross-awareness. Multi-campaign support per brand was explicitly deferred when the Brand Journey shipped.

The term "engagement plan" itself is the collision. It currently maps only to the orchestrator's narrative document — never to the Brand Journey's Flow, which is a single campaign automation artifact. Two different artifact types are wearing overlapping names, which is a plausible root of the confusion driving this ideation.

Navigation is split across two apps. Cockpit (cockpit/, the active surface) is brand-first — a sidebar of brands, each opening a read-only workspace or the Journey — with no campaign or engagement-plan concept visible anywhere in it. The older frontend/ is project-first — a card grid of projects, each opening a four-stage workspace (Planning → Orchestration → Operations → Reporting) — and is where the orchestrator's Engagement Plan and campaign_ops.py flows actually live today.

External pattern. Web research across Salesforce Marketing Cloud, Adobe Journey Optimizer, and Veeva Vault CRM (the closest pharma analog) converges on one shape: Brand (owning entity, own dashboard) → Campaign/Initiative (strategic container, metric rollup) → Journey/Flow (execution artifact, one-or-more per campaign) — with "engagement plan" positioned as the campaign-tier container or a level above individual flows, never as a sibling of "campaign." HubSpot's flat, hierarchy-less campaign model is the named anti-pattern to avoid. Breadcrumb-based drill-through (Brand > Campaign > Journey), paired with a left-nav that re-scopes at each level, is the named UI pattern once a hierarchy goes past two levels.

1Give the brand a first-class campaigns table
Data model & hierarchyConfidence 90%Complexity Medium

Add a real brand_id foreign key to every project and every Brand Journey flow, and introduce one campaigns table that both write into. Today neither system's records point back to a brand at all — orchestrator.run_agents(brand, ...) takes brand as a bare string, and no campaign or project row carries a brand_id. Without this, "how are a brand's campaigns managed" has no query answer: it isn't possible to even list a brand's campaigns today.

Basis
directverified: no brand_id field exists anywhere in projects.py, campaign_ops.py, or orchestrator.py; orchestrator.run_agents(brand: str, therapy_area: str, ...) resolves brand by bare string match against config/brand_kits.json. No /api/campaigns route exists at all — only brand-scoped and project-scoped routes.
Rationale
Every other idea in this document — navigation, rollups, provenance, the formal/ad-hoc fork — is downstream of a campaign having a parent. Doing this once removes the need to bolt on ad-hoc joins later.
Downsides
A real schema migration across two currently-independent stores (projects.db and brand_journey.db); touches every write path into both.
2Resolve the "engagement plan" naming collision
Data model & hierarchyConfidence 85%Complexity Medium

Stop letting "engagement plan" name two different things. All five ideation lenses independently converged on this as the root of the user's own confusion. The recommended shape, matching the external convergent pattern: Engagement Plan becomes the brand-level rollup that sits above campaigns — never a sibling of "campaign," and no longer exclusively the orchestrator's narrative document. The orchestrator's current output gets a narrower, accurate name (e.g. "Campaign Narrative" or "Campaign Brief") scoped to one campaign.

Two alternative shapes surfaced and are worth naming rather than silently dropping: (b) collapse "engagement plan" and "campaign" into one object with two views — a doc view and a flow view — rather than two tiers; (c) a strict three-tier vocabulary borrowed from publishing — Engagement Plan (book) → Campaign (chapter) → Flow (scene) — which forces a containment rule (no flow without a campaign, no campaign without a plan) that closes the "ad-hoc campaign with no engagement plan" edge case for good. All three resolve the collision; they differ on whether Engagement Plan survives as a distinct object at all. That's a real decision, not a detail — pick one before building navigation on top of it.

Basis
directverified: "Brand Engagement Plan" as a term appears only in plan_document.py, orchestrator.py, studio_run.py, persona_review.py, and campaign_artifacts.py — exclusively the orchestrator's narrative artifact, never the Journey's Flow. externalAdobe Journey Optimizer and Salesforce Marketing Cloud both position the plan/initiative tier above individual journeys, never beside them; HubSpot's flat model (no native hierarchy) is the named anti-pattern.
Rationale
This is the single fix with the highest ratio of user-confusion-resolved to engineering effort — largely a rename plus one new rollup concept, not a rewrite of either agent pipeline.
Downsides
Renaming a core, user-facing domain concept touches copy, routes, and prompts across both surfaces; picking the wrong sub-position (b vs. c) now is expensive to reverse once campaigns exist under it.
Sequencing: depends on Idea 1's brand_id/campaigns table existing to have something to roll up.
3One breadcrumb, Brand > Campaign > Flow, replacing two apps
Navigation & wayfindingConfidence 80%Complexity High

Replace Cockpit's flat brand sidebar and frontend/'s flat project-card home with one breadcrumb-driven drill-through — Brand dashboard → Campaign detail → Flow/plan view — with a left-nav that re-scopes at whichever level is selected, instead of two separate top-level apps a user has to remember to switch between. This is the direct structural fix for "I can't figure out how navigation should be spaced out."

Basis
externalnamed pattern from research: "breadcrumb-based drill-through... sidebar alone doesn't scale past 2 levels," confirmed as the convergent solution across Salesforce and Adobe. directverified: Cockpit's App.tsx sidebar is driven solely by listBrands(), with zero campaign-level nav anywhere in that file or in BrandWorkspace.tsx; frontend/'s home is a flat project-card grid with no brand concept.
Rationale
Two disconnected entry points for one hierarchy is exactly what produces the "mishmash" described — collapsing to one navigable structure fixes the complaint at its source, not just its symptom.
Downsides
"Campaign" doesn't exist as a nav-level concept in either surface today, so this breadcrumb is aspirational relative to current code — it's the target shape, not a rename of something that already exists. Determining which surface (Cockpit or frontend/) becomes the surviving shell is a real product decision, not incremental cleanup.
4Formal Engagement Plan vs. ad-hoc Campaign as a creation-time fork
Creation flowsConfidence 65%Complexity Medium

Add one "+ New Campaign" action, available once a brand exists, that asks the user to choose: run the full phase-gated orchestrator (run_agents() — a multi-approval narrative, human-approved per phase) or spin up a single ad-hoc Campaign Flow via the Journey's already-shipped rules-built path. Both back-ends already exist independently today; this makes the choice between them a deliberate, discoverable product decision instead of two undiscoverable apps.

Basis
directthe user proposed this exact distinction unprompted ("maybe you could have a formal engagement plan or ad-hoc campaigns"); confirmed in code — orchestrator.py's PHASE_ORDER = ["align","select","create","deploy"] requires human approval per phase, while the Journey's Flow step (R16/R17) is deliberately lighter-weight and deterministic.
Rationale
Turns the user's own vocabulary into the literal product decision. Cheap relative to its payoff because both code paths are already built — this is surfacing and routing work, not new agent logic.
Downsides
Genuinely depends on Idea 2 settling first — which shape "Campaign" and "Engagement Plan" take decides what this fork is even choosing between. Presenting it before that's settled risks locking in the wrong vocabulary.
Sequencing: the payoff step after Ideas 1 and 2 — the natural next move once a brand has a campaigns table and the naming collision is resolved.
5Kit-gated campaign creation with a versioned lineage snapshot
Provenance & reuseConfidence 85%Complexity Medium

Two things, combined: campaign creation should require an existing confirmed brand kit as its source (no orphan campaigns), and every campaign it creates should stamp the exact kit/message/audience snapshot it was built from. Today brand_journey.py's brand_ctx() reads live kit state with no version pin — so editing a brand's message later silently orphans every campaign already built from the old version, with no way to tell which campaigns still reflect the approved claim. That's a real compliance risk, not a cosmetic gap, in a pharma context.

Three concrete mechanisms surfaced for the versioning half, worth naming as design options rather than committing to one blindly: a git-style branch/commit model (a campaign "branches" from a kit commit and can show how many revisions behind it is); field-level citation like a legal brief (a campaign cites specific kit fields it used, degrading gracefully when a campaign blends multiple kit revisions rather than breaking on one rigid FK); and a franchise-licensing model (kit fields render as "locked" vs. "local" in the flow-builder UI, telling the team exactly what to render differently). The simplest variant — a plain snapshot FK stamped at creation time — is enough to close the immediate gap; the other two are richer answers worth a design pass once the simple version proves the need.

Basis
directverified: brand_journey.py's context builder reads live kit state, not a pinned version; the 2026-09-09 agentic-planning ideation already named "no traceability, no diff/re-validation on edit" as consequences of the missing versioning. externalfranchise licensing and legal-citation as named analogies for centrally-governed-but-locally-executed and partial/graceful provenance, respectively.
Rationale
Without this, multi-campaign reuse (Idea 7) is unsafe — campaigns would be built on kit state that can shift under them with no signal.
Downsides
Requires picking a provenance granularity (whole-snapshot vs. field-level) before implementation; the richer mechanisms are real design investments, not drop-in additions.
6Reconcile CampaignFlow and the Journey's flow onto one schema
Unifying the two systemsConfidence 70%Complexity Medium

campaign_ops.py (used by the orchestrator's Operations stage) and strategy/brand_journey.py (the Journey's Flow step) each independently build a campaign-flow graph, with no shared schema and no path from one to the other today. Reconcile them onto one representation rather than letting two implementations of the same concept keep drifting apart as both get new features.

Verifier correction: the two schemas are not starting from nothing in common — campaign_ops.py's node-type vocabulary and brand_journey.py's FLOW_NODE_TYPES (send/wait/decision/branch/exit/followup/closure) are nearly identical. They clearly evolved from a shared vocabulary; the representations differ (a flat dict vs. a nodes/data.block_code graph with stable IDs), which makes this more tractable than a from-scratch unification — genuinely good news for anyone picking this up.
Basis
directverified via read: shared node-type vocabulary across both modules; no converter exists between the two representations today.
Rationale
Two independently-maintained flow-graph implementations sharing a vocabulary but not a schema is a concrete, fixable root cause of "it's a mishmash" — closing it at the schema level, rather than patching symptoms in the UI, prevents further drift.
Downsides
Touches both strategy/campaign_ops.py and strategy/brand_journey.py — a cross-cutting change that needs a migration plan for any live data in either shape.
7Multi-campaign rollup dashboard per brand
Data model & hierarchyConfidence 70%Complexity Medium

Once a brand has a real campaigns table (Idea 1), add a per-brand view listing every campaign — formal plans and ad-hoc flows together — with status and rolled-up metrics, matching the enterprise pattern where metrics roll up child→parent. This is the feature the user is implicitly asking for ("Brands have separate campaigns — how are those managed?"), and it was explicitly flagged as deferred, not solved, in the Brand Journey's own shipped handoff.

Basis
directverified: "multi-campaign workflows... explicitly deferred" in the 2026-09-24 Brand Journey handoff; no rollup or cross-campaign view exists in either surface today. externalSalesforce and Adobe's metric-rollup pattern, child→parent.
Rationale
The most-cited deferred gap across three separate prior ideation documents — it keeps resurfacing because nothing has closed it yet, and it's the direct answer to the user's own question about managing a brand's campaigns.
Downsides
Has no data to roll up until Idea 1 ships; a smaller version (a live "N campaigns" badge on each brand in the sidebar) is a natural, cheap follow-on once that data exists — but not before.
Sequencing: strictly after Idea 1.
